Filtered directly in SQL (`tense NOT IN (...)` on both the review and new-card queries in `getDueConjugationCardsSplit`) since `tense` is a plain column, unlike vocabulary's JSON `tags` array (see below — `disabledTags` was originally weaker here, since fixed to match). UI: toggle chips in Réglages → Conjugaison, same component as the existing theme chips. Verified against a real in-memory SQLite DB (not just compiled): seeded cards across 3 tenses, disabled one, confirmed it's absent from results and that no filter returns all three. `tsc`/`jest` green (129/129).
- [x] **Keyboard grade shortcuts** (requested 2026-09-06): pressing 1/2/3/4 during review triggers Otra vez/Difícil/Bien/Fácil — `useGradeKeyboardShortcuts` hook (web-only), wired into the 4 review screens that have these buttons (vocab, conjugation, expressions, reading; listening auto-grades, no 4-button UI to hook). - [x] **Per-level (CECRL) vocabulary toggle** (requested 2026-09-10): `AppSettings.disabledLevels` — same strong semantics as `disabledTenses` (total exclusion, including cards already in progress), reusing a new shared `notInClause` helper for both. Verified against a real in-memory SQLite DB: disabling B1 removed it from new cards, and a B1 card already advanced to "learning" *before* disabling still disappeared — confirms the total-exclusion behavior, not just the weaker new-card-only filtering `disabledTags` does. Note: "B2" carries no actual words in the generated dataset (see Later), so disabling it has no visible effect yet.
- [x] **"Lexis cannot be closed" installer failure** (reported 2026-09-10): no Lexis/Electron process was actually running when checked, so the likely cause was the app still being open when the installer ran — normal installer behavior, not a bug. Found and fixed one real contributing edge case anyway: `captionsFetcher.ts`'s hidden `BrowserWindow` counts as an open window for Electron, so if the user closed the main window while a captions fetch was still in flight, full process exit could lag up to ~9s behind the visible window closing. `before-quit` now force-destroys any remaining windows immediately.
- [x] **Listening search returned no results** (reported 2026-09-11): same CORS bug class as DeepL/Open Library, just never applied to this feature — `searchYoutubeVideos`/`fetchVideoMetadata` called `fetch` directly from the renderer against two endpoints confirmed (via `curl`) to send no CORS headers, so both were silently blocked, degrading to `[]`/`null` by existing design rather than an error. Moved both to the main process via IPC (`searchIpc.ts`). Verified for real: called outside a browser context, both return genuine data (7 results for a test query, correct metadata for a direct video ID).
- [x] **"Écrire les mots" vocabulary mode** (requested 2026-09-11): a second way to review vocabulary alongside the existing flashcards — English word shown, Spanish typed and checked (`isExactMatch`, already shared with listening dictation), then the same 4 grade buttons self-grade like conjugation's typed mode. `WritingReviewScreen.tsx` + `WritingReviewContainer.tsx`, new `vocabWriting` session type in `RootTabs.tsx`, a second button on Aujourd'hui. Deliberately reuses `getDueCardsSplit`/`getMoreNewCards` byte-for-byte from the flashcards container — same due-card pool, same `disabledTags`/`disabledLevels` filters, no separate filtering logic to maintain or diverge. `tsc`/`jest` green (129/129); the tag/level filtering itself isn't re-tested here since it's the identical, already-verified function calls, not new logic.
- [x] **Theme deselection didn't actually work — confirmed BUG, now fixed** (reported 2026-09-11): user disabled every theme except "cuerpo" but kept seeing other themes' words. Root cause confirmed directly against the user's real database: `disabledTags` had only ever filtered *new* cards (original, documented design) — 62 cards already past "new" existed in their real data, 57 outside the one enabled theme, all still surfacing regardless of the toggle. Fixed to match `disabledLevels`/`disabledTenses`'s total-exclusion semantics, using SQLite's `json_each` (JSON1 extension, confirmed available under `node:sqlite`) to filter the JSON `tags` array directly in SQL on both the review and new-card queries — removes the old JS-filter/over-fetch-margin workaround entirely. Verified by reproducing the exact reported scenario in a test DB (a tag disabled after a word from it was already "learning") — confirmed absent from results.
- [x] **Favor new words over already-seen ones** (requested 2026-09-11, vocabulary and conjugation): `pickWeighted` (`utils/shuffle.ts`) — the "next card" pick in all three review containers (flashcards, écriture, conjugaison) now counts each new (never-reviewed) card 3× in the draw instead of once, without changing the actual due-card count used elsewhere (Aujourd'hui's "X cartes dues"). Verified statistically (100,000 draws): a pool of 3 review + 1 new card went from a 25% (uniform) to a ~50% chance of drawing the new card, matching the expected math for a 3× weight.
- [x] **Video audio playing in the background while adding it** (reported 2026-09-12): the hidden `BrowserWindow` used to fetch captions loads the real `youtube.com/watch` page, which autoplays — `show: false` only hides the window, it doesn't mute it. Fixed with `webContents.setAudioMuted(true)` right after window creation.
- [x] **Captions returning 0 segments on every video — confirmed BUG, now fixed** (reported 2026-09-12): three real, distinct bugs found by live-testing every stage of the pipeline, not by guessing — see `docs/AUDIT.md` Facts for the full diagnosis (GDPR consent-dialog backdrop swallowing clicks because of this test environment's EEA network location, the transcript button needing the description expanded first, and — the decisive one — YouTube having renamed its transcript-panel endpoint from `get_transcript` to `get_panel` with a new "ViewModel" JSON shape that neither the URL filter (`captionsPreload.ts`) nor the body parser (`transcriptParsing.ts`) recognized. All three fixed; DOM-scraping was confirmed to remain unreliable in this hidden-window context even after every other fix (the panel's lazy-load mechanism never fires while non-visible), so the fix relies on intercepting the network response directly instead. **Verified end-to-end**: `fetchTranscriptForVideo` against the rebuilt `electron-dist` output returned 23 real Spanish segments for a real video. `tsc` (app + electron) and `jest` green, including new unit tests for the `get_panel` JSON parser.
- [x] **"Répétition" mode (shadowing)** (requested 2026-09-13, scoped via a clarifying question after the initial "Language Reactor" idea turned out to mean something more specific): plays a whole video segment-by-segment through its subtitles, auto-pausing after each sentence so the user can repeat it aloud, then resumes only on a manual "Continuer" tap — no auto-advance, no SM-2 grading (same non-graded status as `ReaderScreen.tsx` for books). New `ShadowingScreen.tsx`, launched from a per-video button (🗣) in the Écoute → Bibliothèque list, new `shadowingVideo` state in `RootTabs.tsx` alongside `activeBookId`. New `getListeningVideoSegments` (`database.ts`) returns a video's segments in chronological order — distinct from `getDueListeningCardsSplit`, which mixes videos and filters by due SM-2 card. Also fixed a real correctness gap found while building this: `YouTubePlayer.tsx`'s `onSegmentEnded` callback existed but was never actually reliable/used — it only fired on the IFrame API's "ENDED" state, which (per the YouTube API's own documented quirk) doesn't reliably fire when the `end` playerVar interrupts a segment mid-video, only when the video's own true end is reached. Now fires from the same 200ms poll that already calls `pauseVideo()`, with a per-effect dedup guard so it fires exactly once per segment. **Verified visually (2026-09-13, see the Facts entry below)** — a real screenshot shows the mode working end-to-end.
- [x] **Three real bugs reported right after shipping the above, all confirmed and fixed the same day (2026-09-13)** — see `docs/AUDIT.md` Facts for the full diagnosis of each:
  1. **The YouTube player was hiding the answer field** ("je vois même pas le champ texte") — its `width: '100%'` had no ceiling, so on a 1280px-wide desktop window it rendered ~1180×664px with no `ScrollView` anywhere to reach what it pushed off-screen. Capped at `maxWidth: 480` (`YouTubePlayer.tsx`) and added a `ScrollView` safety net to both screens that embed it (`ListeningReviewScreen.tsx`, `ShadowingScreen.tsx`).
  2. **The "×" delete button on a video row did nothing** — the REAL cause was not the button itself: `react-native-web`'s `Alert.alert` (used by the desktop target since the migration) is a total no-op (`static alert() {}`), so the confirmation dialog never appeared and its callback never ran — silently, on EVERY `Alert.alert` call in the whole app (10 call sites across 6 files: delete video/word/book, reset progress, several validation messages). New `src/utils/alert.ts` (`showAlert`, backed by `window.alert`/`window.confirm`, which are real in an Electron renderer) replaces every one of them. A second, smaller bug was found and fixed along the way: the 🗣 "Répétition" button added earlier that same day sat only 12px from the delete button — with `AnimatedPressable`'s 14px `hitSlop` on each side, their tappable areas overlapped by 16px, so some clicks aimed at delete landed on 🗣 instead (`ListeningScreen.tsx`, gap widened to 28px).
  3. **"The embedded player doesn't work" — this WAS a real, separate bug, not just bug 1 in disguise** (an earlier pass wrongly concluded otherwise, from testing only against the dev-mode `localhost:8081` path, never the actual packaged `app://` one). The `app://bundle` custom scheme used since Decision 016 (fixing a real blank-screen bug) broke the YouTube IFrame API's `postMessage`-based control channel — YouTube's own widget script rejects it once the host page's origin isn't `http:`/`https:`. Fixed by serving the packaged build over a real local HTTP server instead (`electron/main.ts`, `node:http`, bound to `127.0.0.1`, an OS-assigned port) — but loaded via `http://localhost:<port>`, specifically NOT `http://127.0.0.1:<port>`: that address broke the player a *second*, different way (confirmed reproducible twice), while `localhost` (same server, only the URL's hostname differs) works. Also fixed along the way: the player's error-fallback box (`playerErrorBox` in both `ListeningReviewScreen.tsx` and `ShadowingScreen.tsx`) had no size cap either, so any player failure — under the old `app://` scheme or otherwise — looked exactly as "too big" as the original bug, whatever the actual cause. **Verified real playback** with a screenshot under the exact same server code now in `main.ts` (real YouTube frame, correctly sized, `localhost` origin) — this is the first direct visual confirmation this project has ever had that the official IFrame API approach (Decision 016) genuinely works on this target under its actual production loading path, not just that it compiles.
  All four verified end-to-end via a new technique (see `CLAUDE.md`'s "Visual verification" note): the real app launched standalone against an isolated temp profile, driven via `executeJavaScript`, screenshotted via `webContents.capturePage()`.
- [x] **"Réécouter" (replay) crashed the whole app to a blank page** (reported 2026-09-14, right after confirming the localhost fix above actually restored real playback) — see `docs/AUDIT.md` Facts for the full diagnosis (`YouTubePlayer.tsx` forced a full DOM remount via `key={replayKey}` on replay, but YouTube's IFrame API had already replaced that DOM node with its own `<iframe>`, so React's own unmount later threw `Uncaught NotFoundError: removeChild` with no error boundary — full white-page crash, not just a console warning). Fixed by calling `seekTo`/`playVideo` on the existing player instance instead of remounting anything. **Verified end-to-end**: two consecutive real clicks on "Réécouter" in the actual app, screenshotted, both showing the app fully intact and the video genuinely replaying (previously: blank page, empty `document.body.innerText`, on the very first click).
