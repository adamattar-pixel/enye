# Audit — current state

Snapshot as of 2026-09-04. This is a *current-state* summary, not a changelog — update this file when the state changes significantly, overwriting stale entries rather than appending history.

## Facts

Verified directly from the code/tooling, not assumed:

- **Target platform changed: `mobile/` now ships as a Windows desktop app (Electron wrapping an Expo Web export), not iOS/Expo Go** — see `docs/DECISIONS.md` Decision 016. This was an explicit, validated user decision, not a unilateral choice: Windows only (no Mac/Linux to test against), iOS abandoned rather than kept in parallel, no phone-DB migration (fresh SQLite on first desktop launch), scheduled OS reminders replaced by the in-app "cartes dues" count already shown on the Aujourd'hui tab. `Packages/` (Swift) remains frozen as reference spec, untouched.
- No CI/CD is configured (no workflow files). No lint script in `package.json` — only `tsc --noEmit` and `jest`. Two separate `tsc` targets now exist: the app itself (`tsconfig.json`, excludes `electron/`) and the Electron main process (`electron/tsconfig.json`, Node/CommonJS output to `electron-dist/`, gitignored) — both must stay green.
- `expo-sqlite` is **no longer a dependency at all** (removed, along with `expo-notifications`, `expo-audio`, `react-native-webview`, `react-native-youtube-iframe`) — replaced by `node:sqlite` (Node's own built-in SQLite driver, stable enough in the Node 24.x that Electron 44 bundles; no native npm package to compile) running in the Electron main process, reached from the renderer through a `contextBridge`/IPC bridge (`electron/preload.ts`, `src/data/ipcDb.ts`) that implements the exact same 5-method interface (`execAsync`/`runAsync`/`getFirstAsync`/`getAllAsync`/`withTransactionAsync`, now typed as `LexisDb` in `src/data/dbTypes.ts` instead of expo-sqlite's `SQLiteDatabase`). Every function in `src/data/database.ts` ported with a mechanical type rename only — **zero business-logic changes** — confirmed by `tsc --noEmit` staying clean across ~2000 lines with no manual edits beyond the import/type swap.
- **The whole boot sequence (DB open, schema migration, bundled-content import) has been run for real on this machine, twice** (first launch and a reopen of the same file) — not just compiled. Verified directly by querying the resulting `.db` file with `node:sqlite` from outside the app: `words` = 6002, `cards` = 6002, `conjugation_cards` = 63804, `expression_cards` = 60, `reading_cards` = 15, identical on both runs (confirms `importMissingWords`/etc.'s delta-import logic is idempotent under the new backend). A real Electron window (title "mobile", from the loaded page's own `<title>`) was confirmed alive and responsive to process inspection both times.
- **Not verified**: what actually renders inside that window. No screenshot/browser-automation tool was available in this session to visually confirm layout, navigation, or interaction — "the app boots and the database is real" is a different, weaker claim than "the UI works," and the two should not be conflated. A human needs to actually look at the window.
- Listening captions: the WebView-based interception technique (Decision 010) has been **ported to Electron** (`electron/captionsFetcher.ts` + `electron/captionsPreload.ts`), reusing the same injected scripts (network patch, "Show transcript" click, DOM fallback) and the same pure parsing module (`transcriptParsing.ts`) — but this is a **port of a technique that was confirmed working on iPhone**, run for the first time on this new host (hidden `BrowserWindow`, `contextIsolation: false` for that one window only) — not yet exercised against a real YouTube video on this machine. `fetchVideoCaptions` (the free, no-WebView raw-HTTP first attempt) is unchanged and still runs first.
- Video playback dropped `react-native-youtube-iframe` for the official YouTube IFrame Player JS API called directly (`src/components/YouTubePlayer.tsx`) — no WebView wrapper needed at all on a real browser/Electron renderer, which is a genuine simplification, not just a port. The DOM-click fallback for disabling captions (used on iOS after the official API calls alone proved insufficient) has **no possible equivalent here** — the YouTube player is a cross-origin iframe, its internal DOM is unreachable from host page JS by the browser's own same-origin policy. Only the official `unloadModule('captions')`/`setOption('captions','track',{})` calls remain; whether they're sufficient alone on this target is unconfirmed.
- Livres: DeepL translation and Open Library search were confirmed (via direct `curl` header inspection, not assumption) to be **CORS-blocked from any browser-context `fetch`** — DeepL returns a 403 with no `Access-Control-Allow-Origin`, Open Library's `search.json` sets no CORS headers at all. Both now run in the Electron main process (plain Node, not subject to CORS) and are reached via IPC (`src/services/translateIpc.ts`, `bookImportIpc.ts`); `archive.org` downloads DO set `Access-Control-Allow-Origin: *` and would have worked directly, but were routed through the same IPC path for consistency rather than special-cased. The original `src/services/translate.ts`/`bookImport.ts` are unchanged and now run only in the main process.
- No new local-file-picker was added for EPUB import — the mobile app never had one either (URL/search-add only), so this isn't a parity regression, just an opportunity not taken (Electron's native `dialog.showOpenDialog` would make one easy to add later).
- **Packaging**: `npm run desktop:package` (`expo export --platform web` → `electron-builder --win`) was run for real on this machine and produced `release/win-unpacked/Lexis.exe` plus an NSIS installer artifact. Hit and fixed one real bug along the way: `electron-builder` reads the app's entry point from `package.json`'s `"main"` field, which is already claimed by Expo (`"main": "index.ts"`) — fixed via electron-builder's `extraMetadata.main` override (`electron-dist/electron/main.js`) rather than touching Expo's own field. **The produced installer has not been run/installed** — packaging succeeding is confirmed, a clean install experience is not.

## Issues

Real, identified problems — not hypothetical:

1. **Superseded by the desktop migration, not currently applicable**: the 2026-08-21 iPhone confirmation of listening captions/video playback (previously Issue 1 here) described a mechanism (`react-native-webview`, `react-native-youtube-iframe`) that no longer ships at all — see Decision 010/014 for that history and Decision 016 for why/how it was ported. The *desktop* equivalents are implemented but not yet confirmed working end-to-end against a real video (see Facts above).
2. **~52% of vocabulary tags (3123/6002 words) are the `"divers"` catch-all, not a real theme** — see Decision 012. Unrelated to the desktop migration, unchanged.
3. **No SQLite migration system** — unchanged in spirit, but now also applies across the expo-sqlite→node:sqlite backend swap: a fresh desktop install starts from zero (per the user's explicit choice, not a limitation), so this doesn't bite yet, but the same "no automatic resync" caveat applies going forward exactly as it did on mobile.
4. **CECRL level filter "B2" in Decks & mots is always empty** — unrelated, unchanged, not a priority.
5. Correcting a review grade in Historique only updates the stats log, never the SM-2 card's `due_date` — unrelated, unchanged.
6. **`mobile/AGENTS.md` still tells agents to check Expo SDK v57 docs; `expo": "^54.0.37"` is what's actually installed** — unrelated, unreconciled, unchanged (see Unknowns).

## Unknowns

Needs investigation before being treated as fact:

- **The single biggest unknown right now: does the app actually look and work correctly on screen?** Everything above verified via `tsc`/`jest`/direct `.db` file inspection/process-liveness checks — none of it is a substitute for a human opening the window and using it. This is the next thing to check, not a nice-to-have.
- Whether the ported captions-fetch mechanism (Electron hidden `BrowserWindow`, `contextIsolation: false`) actually captures a real `timedtext` response the same way the iPhone WebView did — YouTube's anti-bot behavior (PoToken generation) is tied to its own page JS running in a real browser engine, which Electron's Chromium provides, but this has not been tried against a live video yet.
- Whether `player.unloadModule('captions')`/`setOption('captions','track',{})` alone (official IFrame API calls, no DOM-click fallback possible here) reliably suppress closed captions — the DOM-click fallback that made this reliable on iOS has no cross-origin-safe equivalent on this target.
- Whether DeepL/Open Library/archive.org calls actually succeed end-to-end from the Electron main process with a real `.env` key configured — the CORS diagnosis (why the renderer-side calls would fail) is confirmed by direct header inspection, but no live translate/search call has been made from the new main-process path yet (no key configured in this session, matching the pre-existing "never called with a real key" gap from before the migration).
- Whether the packaged `Lexis.exe`/NSIS installer actually installs and launches cleanly outside of `win-unpacked` — build succeeded, install was not attempted.
- `mobile/AGENTS.md` tells agents to check Expo SDK v57 docs before writing Expo API code, but `mobile/package.json` pins `expo": "^54.0.37"` — not reconciled, carried over unchanged from before the migration.
- Whether performance is acceptable at current data volume on the new `node:sqlite` backend over repeated real use — the two boot-time imports completed without issue, but no sustained-use session has happened yet.
- **"Livres": whether EPUB parsing works against a REAL epub file** — still unconfirmed, carried over unchanged; `books/parsing.ts` itself was untouched by the desktop migration (pure TS, ported without modification).
- Internet-Archive-sourced books' OCR text quality — unrelated, unchanged, still unverified.
