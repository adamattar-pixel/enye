# Audit — current state

Snapshot as of 2026-09-04. This is a *current-state* summary, not a changelog — update this file when the state changes significantly, overwriting stale entries rather than appending history.

## Facts

Verified directly from the code/tooling, not assumed:

- **Target platform changed: `mobile/` now ships as a Windows desktop app (Electron wrapping an Expo Web export), not iOS/Expo Go** — see `docs/DECISIONS.md` Decision 016. This was an explicit, validated user decision, not a unilateral choice: Windows only (no Mac/Linux to test against), iOS abandoned rather than kept in parallel, no phone-DB migration (fresh SQLite on first desktop launch), scheduled OS reminders replaced by the in-app "cartes dues" count already shown on the Aujourd'hui tab. `Packages/` (Swift) remains frozen as reference spec, untouched.
- No CI/CD is configured (no workflow files). No lint script in `package.json` — only `tsc --noEmit` and `jest`. Two separate `tsc` targets now exist: the app itself (`tsconfig.json`, excludes `electron/`) and the Electron main process (`electron/tsconfig.json`, Node/CommonJS output to `electron-dist/`, gitignored) — both must stay green.
- `expo-sqlite` is **no longer a dependency at all** (removed, along with `expo-notifications`, `expo-audio`, `react-native-webview`, `react-native-youtube-iframe`) — replaced by `node:sqlite` (Node's own built-in SQLite driver, stable enough in the Node 24.x that Electron 44 bundles; no native npm package to compile) running in the Electron main process, reached from the renderer through a `contextBridge`/IPC bridge (`electron/preload.ts`, `src/data/ipcDb.ts`) that implements the exact same 5-method interface (`execAsync`/`runAsync`/`getFirstAsync`/`getAllAsync`/`withTransactionAsync`, now typed as `LexisDb` in `src/data/dbTypes.ts` instead of expo-sqlite's `SQLiteDatabase`). Every function in `src/data/database.ts` ported with a mechanical type rename only — **zero business-logic changes** — confirmed by `tsc --noEmit` staying clean across ~2000 lines with no manual edits beyond the import/type swap.
- **The whole boot sequence (DB open, schema migration, bundled-content import) has been run for real on this machine, twice** (first launch and a reopen of the same file) — not just compiled. Verified directly by querying the resulting `.db` file with `node:sqlite` from outside the app: `words` = 6002, `cards` = 6002, `conjugation_cards` = 63804, `expression_cards` = 60, `reading_cards` = 15, identical on both runs (confirms `importMissingWords`/etc.'s delta-import logic is idempotent under the new backend). A real Electron window (title "mobile", from the loaded page's own `<title>`) was confirmed alive and responsive to process inspection both times.
- **The human confirmed the app actually opens and is usable (2026-09-06)** — first real visual confirmation since the migration. Three real issues reported and fixed:
  1. The default Chromium scrollbar (ugly, no iOS/Expo Go equivalent ever existed) — replaced with a thin custom-styled one (`App.tsx`, injected `<style>` on web only).
  2. Buttons in Decks & mots initially looked flattened — first-pass fix (`minHeight`/`justifyContent`/`alignItems` on the button styles) turned out to be treating a symptom, not the cause (see next point), but is a real robustness improvement in its own right and was kept.
  3. **The real cause, found from a follow-up report ("the block shrinks progressively as words load, fully flattened after ~3s")**: every `FlatList` in the app (7 of them, across `DecksScreen`/`ExpressionsScreen`/`StatsScreen`/`ConjugationScreen`/`ListeningScreen`/`BooksScreen`/`ReaderScreen`) had no `style` prop of its own, only `contentContainerStyle`. Under Expo Go this was harmless; under react-native-web, a `FlatList` without its own `flex: 1` grows its container to fit ALL of its content instead of staying a bounded, internally-scrolling area — inside `ScreenContainer`'s `flex: 1` column, that growth squeezes sibling elements (filter chips, sub-tab buttons, hint text) progressively shorter as more rows render, exactly matching the reported symptom. Fixed by adding an explicit `flex: 1` style to all 7. **This is the kind of bug that will keep recurring anywhere a new `FlatList` is added inside a flex column with siblings above it — give every `FlatList` its own `style={{ flex: 1 }}` (or equivalent) as standard practice on this target, not just `contentContainerStyle`.**
  Both fixes pushed. **Not re-confirmed visually after either fix** — not re-tested this session; a visual-verification technique now exists (see below) but hasn't been pointed at these specific screens.
- **Listening captions: fixed and verified end-to-end (2026-09-12).** The 2026-09-11 "CAPTCHA wall" diagnosis was a snapshot of one bad moment, not the real, reproducible cause — a fresh direct call to `fetchTranscriptForVideo` this session loaded the real page fine. Three real, distinct bugs found by live-testing every stage of the pipeline (button search → click → network response → DOM render) rather than guessing, all now fixed:
  1. **YouTube's GDPR consent dialog (`ytd-consent-bump-v2-lightbox`, shown here because of this test environment's EEA network location) silently ate every click.** Its backdrop (`tp-yt-iron-overlay-backdrop`, opacity 0.3, z-index 2201) covers the whole page; confirmed by capturing `event.target` of a real OS-level click (`sendInputEvent`) landing on the backdrop instead of the transcript button. The old `CLICK_SCRIPT` already tried to dismiss this banner, but only once at a fixed ~1s delay — the dialog itself hydrates slower than that (it shows its own loading spinner first), so the single check almost always missed it. Fixed by polling for it in a loop (up to 10s, mirroring the existing button-search poll) before doing anything else.
  2. **The button-click sequence needed the description expanded first.** The "Mostrar transcripción" button lives inside `#structured-description`, `display:none` until the "...more" description expander is clicked — confirmed via `getBoundingClientRect()` returning all zeros on the description-panel copy of the button until an `#expand` click. A `.click()` call still fires regardless of layout, but `CLICK_SCRIPT` now clicks `#expand` first anyway, to target the same visible copy verified working, and to prefer it via `offsetParent` when duplicates exist.
  3. **The real, decisive bug: YouTube renamed its internal transcript-panel endpoint from `get_transcript` to `get_panel` (new "ViewModel" JSON structure), and this codebase's network interception never noticed.** `captionsPreload.ts`'s `isTranscriptUrl()` only matched `get_transcript`/`timedtext` — confirmed via the Chrome DevTools Protocol (`webContents.debugger`, `Network.getResponseBody`) that the real `get_panel` POST request succeeded (200 OK, 34KB body) with genuine segment data every time, but was never intercepted because its URL matched neither string. Separately, even a fixed URL filter wouldn't have helped: `transcriptParsing.ts`'s parsers only recognized the old `startMs`/`endMs`/`events[].tStartMs` shapes, not the new response's `macroMarkersPanelItemViewModel`/`transcriptSegmentViewModel` structure. Both fixed: `isTranscriptUrl()` now also matches `get_panel`; a new `extractPanelTranscriptSegments()` (recursive walk, not a fixed path — same philosophy as the existing `extractJsonTranscriptSegments()`) parses the new shape, with unit tests using the real captured structure.
  Also confirmed and independently ruled out along the way (kept as documented dead ends so they aren't re-investigated): DOM-scraping the rendered `ytd-transcript-segment-renderer` rows never worked in this hidden-window context even after every layer above was fixed — the panel's own lazy-load/continuation mechanism (`ytd-continuation-item-renderer`, `IntersectionObserver`-driven) never fires while the panel stays non-visible, and forcing its `visibility` attribute plus Electron's offscreen-rendering mode (`webPreferences.offscreen`, which does fix `requestAnimationFrame` throttling — confirmed via a 3-per-2s vs. 61-per-2s tick-rate test) still didn't unstick it. This is why the fix intercepts the network response directly instead of relying on DOM rendering at all — confirmed the more robust path, not just an alternative one.
  **Verified for real, end-to-end**: `fetchTranscriptForVideo('dQw4w9WgXcQ')` against the rebuilt `electron-dist` output returned `{status: 'available', language: 'es', segments: 23 segments}` with genuine Spanish text and correct timestamps (auto-translated captions, since the source video is English and the app requests `es-419`).
- **Listening SEARCH was also broken, separately from captions — fixed 2026-09-11.** Reported as "search itself returns no results." Root cause: `searchYoutubeVideos` (scrapes `youtube.com/results`) and `fetchVideoMetadata` (YouTube's oEmbed endpoint, used for pasting a direct link) both called `fetch` directly from the renderer — confirmed via `curl` that neither endpoint sends an `Access-Control-Allow-Origin` header, so both were CORS-blocked from a browser context (same bug class as DeepL/Open Library, Decision 016, just never applied to this feature). The search degraded silently to `[]` (by existing design, for network failures) instead of throwing, which is exactly why it looked like "no results" rather than a visible error. Fixed by routing both through the Electron main process via IPC (`src/listening/searchIpc.ts`), mirroring `translateIpc.ts`/`bookImportIpc.ts`. **Verified for real**: both functions called directly outside a browser context (equivalent to the main-process environment) returned genuine results — 7 videos for a test query, correct title/channel/thumbnail for a direct video ID.
- Video playback dropped `react-native-youtube-iframe` for the official YouTube IFrame Player JS API called directly (`src/components/YouTubePlayer.tsx`) — no WebView wrapper needed at all on a real browser/Electron renderer, which is a genuine simplification, not just a port. The DOM-click fallback for disabling captions (used on iOS after the official API calls alone proved insufficient) has **no possible equivalent here** — the YouTube player is a cross-origin iframe, its internal DOM is unreachable from host page JS by the browser's own same-origin policy. Only the official `unloadModule('captions')`/`setOption('captions','track',{})` calls remain; whether they're sufficient alone on this target is unconfirmed. **The player itself is now confirmed to genuinely work (2026-09-13)** — see the new Facts entry below; this was an open question since the migration until now.
- **Three real bugs reported right after shipping captions + "Répétition" (a fourth, related one only surfaced once the third was actually re-tested against the real production loading path), all confirmed and fixed the same day (2026-09-13), using a new visual-verification technique (see `CLAUDE.md`'s "Visual verification is now possible" note) that finally settles several previously-"unconfirmed" claims above.** Reported: "the YouTube player is too big, I can't even see the text field; I can't click the × to delete my saved videos; segments ARE detected but the embedded player doesn't work" — then, after the first three fixes, still "the embedded playback didn't start" and "the player is still too big."
  1. **The player really was too big.** `YouTubePlayer.tsx`'s container had `width: '100%'` with no ceiling — on the 1280px-wide desktop window (`electron/main.ts`'s `createWindow()` default), it resolved to ~1180×664px, and neither `ListeningReviewScreen.tsx` nor `ShadowingScreen.tsx` (nor `ScreenContainer.tsx` generally) had a `ScrollView` anywhere, so the overflow was invisible and unreachable, not just visually cramped. **Confirmed via a real screenshot** (Electron's own `webContents.capturePage()`, no external tool needed — see `CLAUDE.md`) showing the answer field pushed off-frame entirely. Fixed: `maxWidth: 480` on the player (→ 270px tall in 16:9, `YouTubePlayer.tsx`), plus a `ScrollView` safety net added to both screens that embed it, for any window size that still doesn't fit.
  2. **The delete bug's real cause was not the button.** `react-native-web`'s `Alert.alert` — used everywhere in this app for confirmations/validation messages since the desktop migration (Decision 016 dropped the real `react-native` package's working native-iOS implementation along with iOS itself) — is `class Alert { static alert() {} }`: a **complete no-op**, confirmed by reading `node_modules/react-native-web/src/exports/Alert/index.js` directly. Every `Alert.alert(...)` call in the whole app (10 call sites across 6 files: `ListeningScreen.tsx` delete-video + unavailable-captions notice, `DecksScreen.tsx` delete-word + 2 validation messages, `BooksScreen.tsx` delete-book, `SettingsScreen.tsx` invalid-time-range + saved-confirmation + **reset-progress, a destructive action users could never actually trigger via its button**, `WritingReviewContainer.tsx`/`ReviewScreenContainer.tsx` no-more-new-words notice) has been silently inert since the migration — no error, no console warning, just nothing happening on click. Fixed with a new `src/utils/alert.ts` (`showAlert`, backed by `window.alert`/`window.confirm` — real, working browser APIs in an Electron renderer, deliberately not a custom `Modal` component, which would reintroduce the same class of `Pressable`/`hitSlop` interaction bug found in point 3 below) swapped into all 10 call sites. **Verified end-to-end for the reported case**: a real click (`sendInputEvent`, real coordinates) on a video's "×", with the resulting `window.confirm` dialog answered via the Chrome DevTools Protocol (`Page.javascriptDialogOpening` → `Page.handleJavaScriptDialog`), actually removed the video from the library list.
  3. A smaller, related bug found in the same investigation: the 🗣 "Répétition" button added earlier the same day sat only 12px (`gap`) from the "×" delete button in `ListeningScreen.tsx`'s `VideoRow` — `AnimatedPressable`'s `hitSlop` (14px on every side, for easier tapping generally) made their actual tappable areas overlap by 16px, so a tap aimed at the left portion of delete could land on 🗣 instead. Fixed by moving the gap between these two specific buttons to 28px (`14+14`, the minimum to avoid any hitSlop overlap at all).
  4. **"The embedded player doesn't work" — a real, separate bug, confirmed after this same list first (wrongly) concluded it wasn't.** The very first pass here fixed the player's size, saw it render and play under the `localhost:8081` dev server, and declared this bug fully explained by bug 1 — a real gap in that verification: every dev-mode test loads via `localhost:8081`, never via the `app://bundle` custom scheme the actual PACKAGED app uses (`app.isPackaged` can't be forced true outside a real package, so the packaged code path had never actually been exercised, only assumed identical). Testing the real `app://` path (replicated in an unpacked diagnostic script for CDP access, since Electron Fuses in the packaged binary block `--remote-debugging-port`/`--user-data-dir` outright — confirmed by a literal `"bad option"` rejection) surfaced a real console error: YouTube's own IFrame widget script (`www-widgetapi.js`) rejects the `postMessage` calls its JS control API depends on once the host page's origin isn't `http:`/`https:` — `"Failed to execute 'postMessage' ... origin ('app://bundle')."` This breaks `unMute()` (video stays silent) and the `getCurrentTime()`/`pauseVideo()` poll (no auto-pause at segment end) even when the raw iframe still loads. **Fixed by replacing the `app://` scheme with a real local HTTP server** (`electron/main.ts`, plain `node:http`, bound to `127.0.0.1` on an OS-assigned port, serving the same `web-build` folder `app://` used to). One more twist, also only caught by testing the real mechanism rather than assuming: loading that server via `http://127.0.0.1:<port>` reproduced a *different* player failure twice in a row (`onError` from YouTube's own API), while `http://localhost:<port>` — the exact same server, only the URL's hostname differs — works; `127.0.0.1` and `localhost` are not interchangeable for YouTube's embed checks even though both resolve to the loopback interface. A smaller bug found in the same pass: the player's error-fallback box (shown when `onError` fires) had no size cap either, in both `ListeningReviewScreen.tsx` and `ShadowingScreen.tsx` — so any player failure, this one included, looked exactly as "too big" as bug 1, independent of its real cause. **Verified real playback** with a screenshot under the exact server code now in `main.ts`: a genuine YouTube frame, correctly sized, `localhost` origin — the first direct visual confirmation this project has had, since the desktop migration, that the official IFrame API approach genuinely works under the app's actual production loading path, not just under dev mode or that it compiles. The full "Répétition" cycle was verified too: the player auto-pauses at each segment's end (confirmed the "Continuer" button's computed `opacity` was `1`, i.e. genuinely enabled, not just present in the disabled state), and clicking it advances the progress counter and transcript text to the next segment correctly. **The user independently confirmed real playback now works** ("l'écoute youtube marche") after installing the rebuilt installer — real-world confirmation, not just this session's own screenshots.
- **"Réécouter" (replay) crashed the entire app to a blank page — fixed 2026-09-14, found immediately after the fix above was confirmed working.** `YouTubePlayer.tsx`'s `replay()` used to force a full remount of the player's container `<View>` via `key={replayKey}`, so React would unmount the old one and mount a fresh one. This is unsafe with the YouTube IFrame API specifically: `new YT.Player(node, ...)` **replaces** `node` in the real DOM with its own `<iframe>` (documented behavior, not an implementation detail) — React's Fiber tree still believes it owns that original node, and when React later actually tries to remove it during the remount's commit phase, the browser throws `Uncaught NotFoundError: Failed to execute 'removeChild' ... the node to be removed is not a child of this node`. With no error boundary anywhere in the tree, this unmounts the *entire* React app — `document.body.innerText` was confirmed empty (a genuinely blank page), matching "the app crashed," not a caught, recoverable error. Normal segment-to-segment transitions (`startTime`/`endTime` changing via "Continuer") never hit this, because they don't change the container's `key` — already confirmed working in the Facts entry above, which is why this bug was specific to "Réécouter." **Fixed** by calling `seekTo(startTime, true)` + `playVideo()` directly on the existing player instance instead of remounting anything — replay no longer needs to destroy/recreate the player at all. Also reset the (separately-tracked, now a ref instead of an effect-local variable) segment-ended notification guard on replay, so a segment that already signalled "ended" once can do so again after being replayed. **Verified end-to-end**: two consecutive real clicks on "Réécouter" against a real seeded video in the actual app, both screenshotted — the app stayed fully intact and the video genuinely restarted playback each time, vs. a blank page on the very first click before the fix.
- Livres: DeepL translation and Open Library search were confirmed (via direct `curl` header inspection, not assumption) to be **CORS-blocked from any browser-context `fetch`** — DeepL returns a 403 with no `Access-Control-Allow-Origin`, Open Library's `search.json` sets no CORS headers at all. Both now run in the Electron main process (plain Node, not subject to CORS) and are reached via IPC (`src/services/translateIpc.ts`, `bookImportIpc.ts`); `archive.org` downloads DO set `Access-Control-Allow-Origin: *` and would have worked directly, but were routed through the same IPC path for consistency rather than special-cased. The original `src/services/translate.ts`/`bookImport.ts` are unchanged and now run only in the main process.
- No new local-file-picker was added for EPUB import — the mobile app never had one either (URL/search-add only), so this isn't a parity regression, just an opportunity not taken (Electron's native `dialog.showOpenDialog` would make one easy to add later).
- **Packaging**: `npm run desktop:package` (`expo export --platform web` → `electron-builder --win`) produces `release/win-unpacked/Lexis.exe` plus an NSIS installer. **The installer has since been run for real, repeatedly, by the human** (confirmed working, not just built) — several real issues hit and fixed along the way: (1) `electron-builder` reads the app's entry point from `package.json`'s `"main"` field, already claimed by Expo — fixed via `extraMetadata.main`. (2) Blank white screen on launch (2026-09-07) — Expo's web export uses absolute asset paths, which break under `file://`; fixed by serving via a custom `app://` scheme (later replaced by a real local HTTP server on 2026-09-13 — see the Facts entry above — because that scheme broke the YouTube player's `postMessage`-based control channel). (3) "Failed to uninstall" on a later install attempt (2026-09-11) — the previously-installed copy was in a broken partial state (mismatched file timestamps, consistent with an earlier interrupted update), which made the new installer's automatic "silently uninstall the old version first" step fail; resolved by manually removing the stale install (program files + registry entry — confirmed the SQLite progress file lives in a separate `AppData\Roaming\mobile` folder, untouched by this). Install location itself is `%LOCALAPPDATA%\Programs\mobile` (from `package.json`'s `"name"`, not `productName` "Lexis") — a cosmetic mismatch, not a bug.
- **Vocabulary theme deactivation (`disabledTags`) was confirmed broken against the user's real data, then fixed (2026-09-11).** Reported: disabling every theme except "cuerpo" still surfaced other themes' words. Confirmed root cause by querying the user's actual `lexis-en.db` directly: 62 cards already past `lifecycle: 'new'`, 57 of them outside "cuerpo" — `disabledTags` had only ever filtered brand-new cards (its original, documented design), never ones already in progress, unlike `disabledLevels`/`disabledTenses`. Fixed to match their total-exclusion behavior using SQLite's `json_each` (JSON1, confirmed present in `node:sqlite`) to filter the JSON `tags` array in SQL on both queries — the old JS-filter/over-fetch-margin workaround is gone. Verified by reproducing the exact failure (a word already "learning" before its only tag got disabled) in a test database — confirmed excluded after the fix.
- **New cards are now weighted to appear more often than already-seen ones** (requested 2026-09-11, vocabulary flashcards + écriture + conjugation) — `pickWeighted` (`utils/shuffle.ts`) gives each never-reviewed card 3× the draw weight of a due review card when picking "what's next," without altering the actual due-card counts shown elsewhere. Verified with a 100,000-draw simulation: a 3-review/1-new pool went from 25% to ~50% chance of drawing the new card, matching the expected math.
